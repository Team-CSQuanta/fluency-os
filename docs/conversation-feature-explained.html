1. What this is

FluencyOS is a local-first language-learning desktop application. Everything that matters — the speech recogniser, the language model, the voice, the database — runs on the user's own machine. The conversation feature is the part of the app where that promise is most visible and most demanding: it holds a spoken conversation with the learner, in real time, using three separate AI models at once, on consumer hardware. This document explains the repository layout, then walks through how that feature actually works, then reproduces every file that implements it in full.

3. How the three processes fit together

The application is three operating-system processes, not one. 1. The Electron main process is the only part with real OS access. On launch it picks a free TCP port, mints a random token for this launch only, and spawns the Python backend with both as command-line flags. It then creates the window. Nothing else in the app may read a file or spawn a process. 2. The renderer is ordinary Chromium running React. It has no Node access at all; a contextBridge in the preload script exposes a short, explicit list of functions and nothing more. It reaches the backend over plain HTTP on 127.0.0.1, attaching the handshake token to every request. 3. The Python backend is FastAPI over SQLite. It holds the models, the database and all the logic. Every route depends on require_token, so no other process on the machine can call it even though the port is open locally.
┌──────────────────────┐ spawn (--port --token --db-path) ┌────────────────────┐ │ Electron main │ ───────────────────────────────────▶ │ Python backend │ │ window, files, IPC │ │ FastAPI + SQLite │ └──────────┬───────────┘ └─────────┬──────────┘ │ contextBridge (preload) │ ▼ │ ┌──────────────────────┐ HTTP 127.0.0.1 + X-FluencyOS-Token │ │ Renderer (React) │ ───────────────────────────────────────────────┘ │ no Node access │ └──────────────────────┘
The consequence worth remembering: the renderer never touches a model, a file or the database. Every capability it appears to have is a request to the backend.

4. The conversation feature

A conversation session is a guided spoken (or typed) practice run. The learner picks a scenario — free chat, a job interview, a doctor's visit — and the system injects a handful of words from their own vocabulary that are due for review. The AI plays the other side of the conversation and is told to work those words into what it says. At the end, the session is analysed and the results feed back into the spaced-repetition scheduler. Three models are involved, and on the hardware this app targets they cannot all be resident at once without care:
RoleEngineWhere
Speech → textfaster-whisper tiny.envoice/stt_engine.py
The replyllama.cpp (local) · OpenRouter · Geminivoice/llm_chat_engine.py and friends

Because of that, models are not loaded on demand. The learner presses “Launch AI” explicitly, and until they do, the conversation endpoints refuse with a message that says what to do. That gate is _ensure_launched() in the service.

5. The journey of one spoken turn

This is the path of one spoken turn, and it is the single most useful thing to understand about the feature. Every numbered step is a real function.
Renderer Backend Engines ──────── ─────── ─────── useVadRecorder detects speech and captures the utterance │ │ POST /conversation/sessions/{id}/turns (multipart audio) ▼ submit_user_turn() │ ├─ 1. stt_engine.transcribe(bytes) ──▶ faster-whisper │ returns (text, confidence, speech_seconds) │ ├─ 2. get_turns() → history │ ├─ 3. normalise_for_chat(history) │ enforces strict user/assistant alternation │ ├─ 4. _generate_reply() ─────────────▶ llama.cpp │ / OpenRouter │ / Gemini │ ├─ 5. _insert_turn() × 2 (user, then assistant) │ generation happens BEFORE persistence │ └─ 6. reply_chunking.split_for_streaming() → 2 chunks │ chunk 0 synthesised now │ ◀── TurnSubmitOut (text + audio_chunks) ▼ plays chunk 0, requests chunk 1 │ GET /conversation/turns/{id}/audio?chunk=1 ▼ ensure_audio_chunk() ───────────────────▶ Pocket TTS
Why generation happens before persistence (step 5). If the user turn were written first and the model then failed, the session would be left with a user turn and no reply — and the next request would rebuild a history ending on the user, which the chat template rejects. Generating first means a failure leaves the database exactly as it was. Why the history is normalised (step 3). Gemma's chat template requires strict user / assistant / user / assistant alternation starting with user. This was measured, not assumed: a history of system + assistant + user fails outright, while system + user + assistant + user works. Before normalise_for_chat existed, every conversation died immediately after the greeting, because the greeting is an assistant turn and it came first. The function collapses consecutive same-role turns and drops a leading assistant message. Why the reply is split into two chunks (step 6). Pocket TTS is autoregressive, so the first audio arrives sooner for a shorter piece of text. Splitting the reply in two and synthesising only the first chunk before responding cuts the silence the learner sits through. The split point is chosen at a sentence boundary by reply_chunking.split_for_streaming. Two was measured as better than one, and more than two gave no further benefit while making the prosody audibly restart.

6. The engines

Three providers, one interface. The learner may run the model locally or supply an API key. llm_target() resolves which, and _generate_reply() dispatches on it. The local path is llama.cpp through llama-cpp-python; the cloud paths are OpenRouter and Gemini. All three expose the same two functions — generate_chat and generate_json — so the service never branches beyond the dispatcher. Model JSON is not trusted. Small local models routinely emit JSON wrapped in prose, fenced in markdown, or with an unclosed bracket. Rather than failing the analysis, voice/json_utils.py strips fences, finds the outermost object, and repairs unbalanced brackets before parsing. This is why a session still produces a report when a 1B model rambles. Loading and unloading. launch_engines() loads exactly the engines the chosen channel needs — text needs the LLM only, voice needs all three — and unload_engines() frees them. The app also unloads on quit, so closing the window returns the memory.

7. The post-session report

When a session ends, end_session() produces a report. Its design has one rule: every number is either computed or judged, and the two are never mixed.
Computed from the transcriptJudged by the model
words per minute (from real speech seconds)grammatical precision
filler rate per 100 wordsthe three most instructive errors
average response delayself-corrections
longest uninterrupted runper-word usage classification
type–token ratio, above-level wordssummary
The judged half is described by a single Pydantic model, LlmReportAnalysis, and the prompt that asks for it is rendered from that model's own fields. The prompt therefore cannot drift from what the reader parses — a class of bug that had previously left four report fields permanently zero, because three copies of the prompt asked for different keys than the reader consumed. Speech time is real. words_per_minute divides learner words by the summed duration of recognised speech segments, not by wall clock — wall clock includes the model thinking and the AI talking, and is not a speech rate. A text-channel session reports None rather than a number that means nothing. Results feed the scheduler. Each target word's usage is rated on the same scale a flashcard answer uses — spontaneous → Easy, prompted → Good, incorrect → Again, avoided → Hard — and applied through the same FSRS code path. Using a word in conversation moves its schedule exactly as recognising it on a card would. That is the central argument the project makes, and review.apply_conversation_outcomes() is where it happens.

8. The renderer side

The store owns the session; the screen owns the microphone. conversationStore.ts is a Zustand store holding the session, its turns, the engine status and the report. It never touches audio hardware — every method is a request. Voice capture is voice-activated, not push-to-talk. useVadRecorder.ts holds the microphone open, measures frame energy, and decides when an utterance starts and ends. Two details matter: it keeps a rolling pre-roll buffer so the first syllable is not clipped, and it raises its threshold while the AI is speaking so the reply coming out of the speakers does not trip detection and interrupt itself. Word-by-word highlighting. spokenTiming.ts distributes the reply's words across the known duration of each audio chunk, weighted by word length, so SpokenText.tsx can light up each word as it is spoken. It is an estimate — Pocket TTS does not return word timings — and it is deliberately an even, length-weighted estimate rather than a guess dressed up as data.

329def normalise_for_chat(pairs: list[tuple[str, str]]) -> tuple[list[str], list[tuple[str, str]]]:
330 """Reshape a transcript into something every provider will accept.
331 
332 Returns (assistant_opening_lines, history), where history begins with a
333 'user' message and strictly alternates user/assistant.
334 
335 Two real failures make this necessary, both observed in production:
336 
337 1. **A session opens with the AI speaking.** Gemma's chat template rejects
338 that outright — measured against gemma-3-1b, ``system + assistant +
339 user`` raises "Conversation roles must alternate
340 user/assistant/user/assistant/...", while ``system + user + assistant +
341 user`` is fine. So every reply after the AI greeting failed on any
342 Gemma model. Leading assistant turns are lifted out here and handed to
343 the caller to fold into the system prompt, which keeps their content
344 without breaking the alternation rule. Gemini requires the same shape.
345 
346 2. **Consecutive turns from one speaker.** A failed generation used to
347 leave the learner's turn committed with no reply, so the next attempt
348 saw two user turns in a row and hit the same template error — the
349 error then masked whatever had actually gone wrong. Orphans are no
350 longer created (see submit_user_turn), but sessions already in that
351 state still have to work, so same-role runs are merged into one
352 message rather than dropped.
353 """
354 merged: list[tuple[str, str]] = []
355 for role, text in pairs:
356 clean = (text or "").strip()
357 if not clean:
358 continue
359 if merged and merged[-1][0] == role:
360 merged[-1] = (role, f"{merged[-1][1]} {clean}")
361 else:
362 merged.append((role, clean))
363 
364 opening: list[str] = []
365 while merged and merged[0][0] == "assistant":
366 opening.append(merged.pop(0)[1])
367 return opening, merged

541def ensure_audio_chunk(turn_id: str, text: str, index: int, engine: str = tts.DEFAULT_ENGINE) -> Path:
542 """Synthesizes one sentence of a reply, cached on disk after the first
543 request. Called when that sentence is about to be played rather than while
544 the learner is still waiting to read the reply."""
545 name = tts.normalise(engine)
546 chunks = tts.engine_for(name).split_for_streaming(text)
547 if index < 0 or index >= len(chunks):
548 raise IndexError(f"chunk {index} out of range for {len(chunks)} chunks")
549 path = audio_chunk_path(turn_id, index, name)
550 if not path.exists():
551 audio = tts.engine_for(name).synthesize(chunks[index])
552 # Written to a private temp file and moved into place, never straight
553 # to `path`. The player fetches chunk N+1 while N is still audible, so
554 # two requests for the same chunk really can overlap (a replay, a
555 # retry, a second window) — and a FileResponse reading a path that
556 # another thread is still writing serves a truncated WAV, which plays
557 # as a click or as silence. os.replace is atomic, so a reader sees
558 # either the whole file or no file.
559 tmp = path.with_suffix(f".{uuid7()}.part")
560 try:
561 tmp.write_bytes(audio)
562 os.replace(tmp, path)
563 finally:
564 tmp.unlink(missing_ok=True)
565 return path

663def end_session(conn: sqlite3.Connection, session: sqlite3.Row) -> dict:
664 target = _session_llm_target(conn, session)
665 _ensure_launched({"llm"}, llm_target=target)
666 turns = get_turns(conn, session["id"])
667 target_word_ids = json.loads(session["target_word_ids"])
668 target_words = (
669 conn.execute(
670 f"SELECT id, word FROM vocab_words WHERE id IN ({','.join('?' for _ in target_word_ids)})",
671 target_word_ids,
672 ).fetchall()
673 if target_word_ids
674 else []
675 )
676 
677 transcript = [(t["speaker"], t["text"]) for t in turns]
678 analysis = _generate_analysis(target, transcript, [w["word"] for w in target_words])
679 
680 cefr_row = conn.execute("SELECT cefr_level FROM users WHERE id = ?", (session["user_id"],)).fetchone()
681 target_cefr = conversation_report.resolve_cefr(cefr_row["cefr_level"] if cefr_row else None)
682 metrics = conversation_report.compute_metrics(turns, target_cefr)
683 
684 user_turns = [t for t in turns if t["speaker"] == "user"]
685 ai_turns = [t for t in turns if t["speaker"] == "ai"]
686 routing = []
687 outcomes_for_logs: list[tuple[str, str]] = []
688 for w in target_words:
689 # Whether the learner said the word at all is a fact about the
690 # transcript, not a judgement — so it is established here, not asked.
691 evidence_turn = next(
692 (t["turn_index"] for t in user_turns if conversation_report.says_word(t["text"], w["word"])),
693 None,
694 )
695 outcome = conversation_report.match_word_usage(analysis.word_usage, w["word"]) or "avoided"
696 
697 if evidence_turn is not None and outcome == "avoided":
698 # "avoided" means "never used at all", and the transcript shows
699 # otherwise — a claim the evidence disproves, so it does not
700 # stand. Observed with gemma-3-1b marking every word avoided in a
701 # session where the learner had plainly used all three; the report
702 # then read 0/3 and the words were logged as unpractised, pushing
703 # them back to the front of the queue they had just earned their
704 # way out of.
705 #
706 # Only this one outcome is corrected. "incorrect" is a judgement
707 # about *how* the word was used and nothing here can second-guess
708 # it; "avoided" is the only verdict that is checkable.
709 said_first = any(
710 t["turn_index"] < evidence_turn and conversation_report.says_word(t["text"], w["word"])
711 for t in ai_turns
712 )
713 # The spec's own distinction: prompted means used only after the
714 # AI said it. That much is visible in the transcript.
715 outcome = "prompted" if said_first else "spontaneous"
716 
717 routing.append({"word": w["word"], "outcome": outcome, "evidence_turn": evidence_turn})
718 outcomes_for_logs.append((w["id"], outcome))
719 
720 correct_count = sum(1 for r in routing if r["outcome"] in ("spontaneous", "prompted"))
721 # None, not 0: a session with no target words didn't score zero accuracy,
722 # it had nothing to be accurate about.
723 contextual_accuracy_pct = round(100 * correct_count / len(routing)) if routing else None
724 
725 report = {
726 "report_version": conversation_report.REPORT_VERSION,
727 "session_id": session["id"],
728 "contextual_accuracy_pct": contextual_accuracy_pct,
729 "grammatical_precision": analysis.grammatical_precision,
730 # Type-token ratio is 0-1; the dial needs 0-100.
731 "lexical_range": round(100 * metrics.type_token_ratio),
732 "pronunciation_score": metrics.pronunciation_score,

2 *
3 * Neither TTS engine reports word timings, and forcing an alignment would
4 * cost more than the feature is worth. What we have instead is exact: the
5 * clip's real duration and its exact text. Distributing the words across that
6 * duration by their spoken weight is an estimate, but it is anchored at both
7 * ends and re-read from `audio.currentTime` every frame — so it cannot drift,
8 * and a stall or a slow chunk moves the highlight with the sound rather than
9 * away from it.
10 */

12/** Roughly how long a word takes to say, relative to other words.
13 *
14 * Length dominates, but not from zero: even a one-letter word takes time to
15 * articulate, so there is a floor. Trailing punctuation buys extra weight
16 * because the pause after a comma or a full stop is real time during which no
17 * new word is being said — without it every sentence-final word lights up
18 * early and the highlight runs ahead of the voice for the rest of the clip. */
19export function wordWeight(word: string): number {
20 const letters = word.replace(/[^\p{L}\p{N}']/gu, '').length;
21 let weight = 1 + letters;
22 if (/[,;:]$/.test(word)) weight += 1.5;
23 if (/[.!?…]$/.test(word)) weight += 2.5;
24 if (/[—–-]$/.test(word)) weight += 1;
25 return weight;
26}

36/** Splits a chunk into words, each with the slice of the clip it occupies.
37 * Whitespace is kept on the word it follows so re-joining reproduces the
38 * original text exactly. */
39export function timeWords(chunk: string): TimedWord[] {
40 const tokens = chunk.match(/\S+\s*/g) ?? [];
41 const weights = tokens.map((t) => wordWeight(t.trim()));
42 const total = weights.reduce((a, b) => a + b, 0);
43 if (total <= 0) return [];
44 
45 let acc = 0;
46 return tokens.map((text, i) => {
47 const start = acc / total;
48 acc += weights[i];
49 return { text, start, end: acc / total };
50 });
51}

53/** How many words of `timed` have been reached at `fraction` through the clip.
54 *
55 * A word counts as spoken once the voice has *started* it, not once it has
56 * finished — highlighting on completion always reads as lagging, because the
57 * listener has already heard the word by then. */

59 if (fraction <= 0) return 0;
60 if (fraction >= 1) return timed.length;
