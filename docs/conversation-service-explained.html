2. What you need to know first

The code uses a fairly small set of ideas over and over. Learn these nine and almost nothing in either file will look unfamiliar.

2.1  Talking to the database (sqlite3)

SQLite is a database that lives in a single file. Python talks to it through three things you will see constantly:

ThingWhat it is
connA connection — an open line to the database file. Every function here takes one as its first argument rather than making its own, so the whole HTTP request shares one connection.
conn.execute(sql, params)Runs one SQL statement and hands back a cursor you can read rows from.
.fetchone() / .fetchall()Take one row, or every row, from that cursor. fetchone() gives None if there were none — which is why you see so many if row is None checks.

The ? placeholder. You will never see a value pasted into a SQL string here. Instead:

Never: f"SELECT * FROM t WHERE id = '{user_id}'"
Always: conn.execute("SELECT * FROM t WHERE id = ?", (user_id,))

The ? is a hole the database fills in itself, keeping the value strictly a value. If it were pasted into the string, a user id containing SQL would become SQL — that is SQL injection. Note the comma in (user_id,): that trailing comma is what makes it a one-item tuple rather than just brackets around a variable, and leaving it out is a genuinely common beginner error.

sqlite3.Row. This project configures rows so you can read columns by name — row["word"] — instead of by position. When you see a parameter typed sqlite3.Row, picture "one record from the database, read like a dictionary".

conn.commit(). SQLite holds your writes in a transaction until you commit. Until then, nothing is permanent and other writers may be blocked. That is why you will see commits placed deliberately, and why one comment in start_session is specifically about not holding a transaction open across a slow AI call.

2.2  Type hints

The part after a colon or an arrow is a hint. Python does not enforce it at runtime; it is documentation that editors and checkers can verify.

def get_turns(conn: sqlite3.Connection, session_id: str) -> list[sqlite3.Row]:

Reads as: takes a connection and a string, gives back a list of rows. Two forms worth knowing:

  • str | None — "a string, or nothing". The | means "or".
  • list[tuple[str, str]] — a list of pairs of strings. This exact type is the conversation history: [("user", "hello"), ("assistant", "hi there")].

2.3  f-strings

A string prefixed with f can contain {expressions} that are evaluated and inserted. f"cloud:{target['model']}" becomes "cloud:gpt-4". Used here mostly to build labels and, carefully, to build the ?,?,? part of a SQL statement — never the values themselves.

2.4  Comprehensions and generator expressions

A compact way to build a list from another list.

user_turns = [t for t in turns if t["speaker"] == "user"]

"For each t in turns, keep it if the speaker is the user." The same shape inside round brackets is a generator — it produces items one at a time instead of building a whole list, which is what sum(...) and any(...) want:

fillers = sum(1 for w in all_words if w in FILLER_WORDS)

"Produce a 1 for every filler word, and add them up" — i.e. count them.

2.5  next(..., None) — first match or nothing

evidence_turn = next((t["turn_index"] for t in user_turns if ...), None)

Take the first item the generator produces and stop looking; if it produces none at all, give back None. Without that second argument it would raise an error instead. This is the idiom for "find the first thing matching, or nothing".

2.6  The * in a function signature

def start_session(conn, *, user_id: str, scenario: str, channel: str):

Everything after the bare * must be passed by name: start_session(conn, user_id=..., scenario=...). You cannot pass them positionally. This is deliberate — scenario and channel are both strings, and positionally there would be nothing to stop you swapping them.

2.7  The leading underscore

_generate_reply, _audio_dir, _words. A leading underscore is a convention meaning internal to this file — not part of what other modules should call. Python does not enforce it. In these two files the distinction is real and useful: the names without underscores are the feature's public surface, and there are only about fifteen of them.

2.8  Pydantic — models that validate themselves

A BaseModel is a class that describes a shape of data and checks incoming data against it.

class ReportError(BaseModel):
    bad: str
    good: str
    why: str

Hand it a dictionary through model_validate(...) and it either gives you a proper object or raises ValidationError. This matters enormously here, because the data being validated comes from a language model, which is free to return anything at all. Field(default=..., description=...) attaches both a fallback value and a human description to a field — and §5.4 shows the clever thing this file does with those descriptions.

2.9  @dataclass(frozen=True)

A decorator (the @ line) modifies the class below it. @dataclass writes the boilerplate constructor for you from the field list. frozen=True makes instances immutable — once a TranscriptMetrics is built, nobody can quietly change a number inside it. For a value that represents a measurement, that is exactly right.

One more, and it is the most important idea in either file: None is not zero. Throughout this code, None is used to mean "this could not be measured", kept strictly apart from 0 meaning "measured, and it was zero". A text conversation has no speaking speed — reporting 0 words per minute would be a lie about the learner. Watch for this distinction; it drives several branches you would otherwise find puzzling.

3. The shape of the two files

Before the line-by-line, here is the shape of the thing. The Conversation feature lets a learner hold a spoken or typed conversation with an AI, which is told to work the learner's own vocabulary words into what it says. Afterwards the conversation is analysed, and the results feed the flashcard scheduler.

conversation.py has three public entry points that matter. Everything else in the file exists to serve them.

start_session() line 437 Learner opens a conversation. │ Picks target words, asks the AI to greet them, │ writes the session and turn 0. │ submit_user_turn() line 597 Learner says or types something. │ Transcribe → reshape history → generate reply │ → write both turns. │ Called once per exchange, many times. │ end_session() line 663 Learner leaves. Ask the AI to judge, compute the numbers, write the report, feed the scheduler.

conversation_report.py is the analysis half, and it is built around one rule stated in its own docstring:

Every field in the report is either DETERMINISTIC or JUDGED, and the two never mix. Deterministic means computed from the transcript by plain arithmetic — reproducible, free, testable. Judged means asked of the language model, because it genuinely needs understanding of language. A model asked for a "fluency score" will happily invent one; a model asked whether a learner used a word correctly is doing work only a language model can do.

6.3  Five ways to break this code

  1. Writing the user's turn before generating the reply. You will recreate the orphaned-turn bug: a turn with no reply, then an alternation error on the next attempt that hides the real cause.
  2. Returning 0 where the code returns None. The report will state, confidently, that a learner spoke at 0 words per minute.
  3. Writing the prompt's JSON keys by hand. That is the exact bug the docstring documents — four fields silently zero on every real session, with the tests still green.
  4. Using in for word matching. "art" in "start" is True. Use says_word.
  5. Appending review logs on re-end instead of replacing. One conversation counts twice, and the affected words wrongly drop down the practice queue.

6.4  How to verify a change

The deterministic half is genuinely easy to test, by design — compute_metrics is a pure function, so you can hand it a list of fake turn dictionaries and assert on the numbers with no database and no model. The existing tests are in backend/tests/test_conversation.py and test_conversation_report.py.

But remember how the four-zero-fields bug survived. The tests passed because they fed well-formed data straight into the parser, never exercising the prompt that asked for it. A test that never crosses the boundary you changed will not notice you broke it. For anything touching the prompt, check the generated string itself.
